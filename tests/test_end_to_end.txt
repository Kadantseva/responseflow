uv run pytest -q tests/test_end_to_end.py
Этот скрипт — набор из трёх интеграционных тестов для ResponseFlow Local. Он проверяет полный путь от анализа переписки до обработки найденной проблемы менеджером, защиту от устаревших решений и сохранность структуры базы данных.

В отличие от предыдущего теста, который проверял обнаружение одного сообщения без ответа, здесь дополнительно проверяется работа карточки после её создания.

1. Подготовка: время и файл сообщений

2. Фикстура analysis_service
Это фикстура pytest, которая создаёт сервис анализа.

Она использует готовые зависимости из conftest.py:

message_repository — хранилище сообщений;

finding_service — сервис создания и обновления карточек;

window_builder — компонент формирования контекста переписки.

В сервис подключён только UnansweredDetector, который ищет обращения без ответа.

Фикстура позволяет не создавать AnalysisService вручную в каждом тесте

3. Фикстура prepared_analysis
Эта фикстура подготавливает данные и запускает анализ.

Она выполняет три действия:

Читает сообщения из data/fixtures/messages.jsonl и преобразует их в объекты MessageRevision.

Сохраняет сообщения в репозитории.

Запускает анализ рабочей области north на момент NOW.

Результат — отчёт об анализе.

4. Тест № 1 — полный цикл обработки карточки
Шаг 1. Проверка отчёта
report = prepared_analysis

assert report.workspace_id == "north"
assert report.analysis_time == NOW
assert report.created_findings == 1
assert report.updated_findings == 0

Проверяется, что анализ:

выполнен для рабочей области north;

использовал правильное время;

создал одну новую карточку;

не обновил существующие карточки.
Шаг 2. Проверка созданной карточки
Тест читает карточки из репозитория и проверяет:

карточка существует в единственном экземпляре;

она относится к north;

её тип — unanswered;

статус — open;

версия — 1.
Версия нужна для контроля изменений карточки. Когда менеджер меняет её статус, версия увеличивается.

Шаг 3. Получение подробной информации
detail = inbox_service.get_finding(
    workspace_id="north",
    finding_id=finding.finding_id,
)

assert detail.finding_id == finding.finding_id
assert detail.subject_key == finding.subject_key
Здесь карточка повторно запрашивается через inbox_service.

Проверяется, что подробное представление соответствует сохранённой карточке.
Шаг 4. Менеджер принимает карточку в работу
Создаётся команда принятия карточки.

author — автор действия;

expected_version — версия карточки, которую менеджер видел;

occurred_at — время действия;

comment — комментарий.

Шаг 5. Проверка истории
history = inbox_service.get_history(
    workspace_id="north",
    finding_id=finding.finding_id,
)

assert len(history) == 2
Ожидается два события в истории карточки. Судя по логике теста, это событие первоначального создания карточки и событие её принятия менеджером.

Обрати внимание: проверяется только количество событий, а не их типы. Если важно подтвердить конкретные события, лучше дополнительно проверять event_type.

Итог первого теста: система обнаруживает проблему, создаёт карточку, позволяет менеджеру принять её в работу и записывает историю изменений.
